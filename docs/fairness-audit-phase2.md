## 1. สรุปผู้บริหาร (Executive Summary)

ทำครบทั้ง 3 ฟีเจอร์ บน stack เดิม ไม่มี dependency ใหม่:

| ฟีเจอร์ | ผลที่วัดได้ (Fair mode, 3,840 runs เทียบ baseline Phase 1 ที่ seed เดียวกัน) |
|---|---|
| **A. Late Joiner Baseline** | ช่องว่าง effective games ใน scenario คนมาระหว่างก๊วนลดจาก **9.71 → 1.26** โดยสถิติจริงไม่ถูกแตะ คนมาสายไม่ "กินคิว" ต่อเนื่องอีก (wait p90 ลด 19.6 → 17.1 นาที) |
| **B. Mix Groups** (เปิดเมื่อ host ต้องการ) | กลุ่ม 4 คนซ้ำในช่วงล่าสุดลด **40% → 27%** และตลอด session ลด **54% → 38%** แลกกับคิวรอนานขึ้นเล็กน้อย (wait p90 +0.5 นาที, max consecutive waits +1) |
| **C. Weighted Team Formation** | คู่หูซ้ำในช่วงล่าสุดลด **32% → 19%** (เปิด Mix เหลือ 16%) และ exact rematch ลด **26% → 14%** แลกกับแมตช์ gap 2 ที่เพิ่มจาก **2% → 9%** ส่วน gap ≥3 ยังเกือบ 0 เพราะมี guardrail |

**สิ่งที่ไม่เปลี่ยน:**
- ข้ามคนที่เล่นน้อยกว่า (effective games): **0 ครั้ง**
- ผิดกติกา waiting tolerance: **0 ครั้ง**
- เล่นติดกันโดยไม่จำเป็น: **0 ครั้ง**
- ผิดกติกา Champion Mode: **0 ครั้ง**

ตัวเลขทั้งหมดนี้มาจาก 5,760 simulation runs (baseline 1,920 + Phase 2 3,840) รวมถึงคำสั่งซ้ำ คำสั่งเก่า (stale) และคำสั่งที่ต้องถูกปฏิเสธมากกว่า 150,000 ครั้ง

**Tests: 103/103 ผ่าน** (เดิม 68 + ใหม่ 35 รวมรอบ hardening) · ผลการทดลองน้ำหนักและการแยก metric อยู่ในหัวข้อ 11

**ข้อควรรู้ที่สำคัญที่สุด:**
1. น้ำหนักที่เลือก (**skillGap 7**) ต่างจากค่าเริ่มต้นในสเปก (5) เพราะ simulation แสดงว่าค่า 5 ทำให้แมตช์ gap 2 สูงถึง 12% ดูหัวข้อ 5
2. ข้อจำกัดเดิมยังอยู่: ก๊วนขนาด 8 คน 1 คอร์ทยังมีกลุ่มซ้ำสูง (69% แม้เปิด Mix) เพราะคณิตศาสตร์ของการหมุนเวียนบังคับไว้

## 3. พฤติกรรม Late Joiner Baseline

**นิยาม**

```
effectiveGames = gamesPlayed + fairnessBaseline
```

การเปรียบเทียบความแฟร์ทุกจุดใช้ค่านี้ ได้แก่ ลำดับคิว, tie group, การเลือกตัวสำรองอัตโนมัติ และการคำนวณ baseline ของคนถัดไป

| กรณี | พฤติกรรม |
|---|---|
| เพิ่มผู้เล่นใหม่ (ทั้งช่วง setup และระหว่างเล่น) | `fairnessBaseline` = effective games **ต่ำสุด** ของผู้เล่น *active* ณ ตอนนั้น (ช่วง setup ได้ 0 เพราะทุกคน 0) |
| ผู้เล่น "active" | สถานะ `waiting`, `in_match`, `champion_hold` เท่านั้น ไม่นับ `unavailable` และ `left` |
| ไม่มีผู้เล่น active | baseline = 0 |
| เกมจริง / ชนะ / แพ้ / ประวัติแมตช์ | ไม่ถูกแตะเลย (เริ่มที่ 0) |
| ลำดับคิวเดิม / baseline ของคนอื่น | ไม่เปลี่ยน คนใหม่ต่อท้ายคิว |
| เวลารอ | ไม่สืบทอด: `totalWaitMs = 0`, `waitPasses = 0`, `queuedAt = เวลาที่เข้าร่วม` |
| พักชั่วคราวแล้วกลับ (`unavailable` → คิว) | baseline **คงเดิม** ไม่ได้ baseline ใหม่ |
| ออกแล้วกลับมา (`left` → "กลับเข้าคิว" บน record เดิม) | ตัวตนและสถิติจริงเดิม baseline ถูกยกเป็น `max(baseline เดิม, ค่าต่ำสุดปัจจุบัน − gamesPlayed)` **ไม่มีวันลดลง** จึงไม่ได้สิทธิ์เล่นติดเพื่อไล่ตาม |
| เพิ่มคนใหม่ที่ชื่อซ้ำกับคนที่ออกไปแล้ว | เป็นตัวตนใหม่ (id ใหม่) และถือเป็นคนมาสาย host ควรใช้ "กลับเข้าคิว" ถ้าเป็นคนเดิม |
| ข้อมูลเก่า (Phase 1) ที่ไม่มีฟิลด์ใหม่ | ใช้ค่า 0 / ปิด / ค่า default อัตโนมัติ ไม่เขียนทับสถิติย้อนหลัง (มี test โหลดไฟล์ legacy จริง) |
| Persistence | baseline, waitPasses และ settings อยู่ใน state จึงรอด restart (มี test ด้วย `DATA_FILE`) |

**ผลวัด** (scenario `lateJoiners`, 30% ของผู้เล่นมาสาย):

| | P1 | P2 |
|---|---|---|
| Effective spread (Fair) | 9.71 | 1.26 |
| Effective spread (Champion) | 9.96 | 1.53 |
| เกมจริงเฉลี่ยของคนมาสาย | 7.28 | 5.97 |
| เกมเฉลี่ยของคนที่อยู่ตั้งแต่ต้น | 15.92 | 16.31 |
| wait p90 | 19.6 นาที | 17.1 นาที |
| อัตราการได้เล่นต่อเนื่องทันที | 45% | 42% |

คนมาสายเล่นน้อยลงตามเจตนา เพราะไม่ไล่ตามจำนวนเกมของคนที่มาก่อนแล้ว ขณะที่คนที่อยู่ตั้งแต่ต้นได้เล่นมากขึ้น

**UI:** แสดงเกมจริงเสมอ ส่วนคนที่มี baseline จะมีป้ายเล็ก "มาระหว่างก๊วน" ซึ่ง tooltip เขียนว่า "ผู้เล่นเข้าร่วมระหว่าง Session — ระบบปรับลำดับคิวให้เหมาะสมแล้ว" ไม่แสดงตัวเลข baseline

## 4. อัลกอริทึม Mix Groups

ค่าเริ่มต้นคือ **ปิด** host เปิด/ปิดได้ทั้งก่อนและระหว่างเล่นผ่าน `updateSettings` การเปลี่ยนมีผลตั้งแต่การจัดแมตช์ครั้งถัดไป แมตช์ที่กำลังเล่นไม่ถูกแตะ

**นิยาม "wait pass":** จำนวนครั้งที่มีการจัดแมตช์ (ทุกคอร์ท) ขณะที่ผู้เล่นรออยู่ในคิวแต่ไม่ถูกเลือก
- ถูกรีเซ็ตเมื่อเข้าคิวใหม่
- คนที่กลับหัวคิว (แมตช์ถูกยกเลิก หรือถูกเปลี่ยนตัวออก) ได้ค่า pass เท่ากับคนที่รอนานที่สุดในคิว เพื่อรักษาสิทธิ์หัวคิวไว้

### Stage 1: เลือกว่าใครได้ลง (Fairness First)

1. ทุกคนที่มี effective games **น้อยกว่า** ช่องสุดท้ายได้ลงเสมอ ข้อนี้ห้ามละเมิดทั้ง ON และ OFF
2. **Mix OFF:** ช่องที่เหลือเลือกจากคนที่เสมอกันทั้ง effective games และเวลาเริ่มรอ (พฤติกรรม Phase 1 เดิม)
3. **Mix ON:** ช่องที่เหลือเลือกจากใครก็ได้ใน tier effective games เดียวกัน (สูงสุด 8 คนแรกตามจำนวน pass) ภายใต้ 2 เงื่อนไข:
   - **Waiting tolerance = 1:** คนที่ถูกข้ามต้องมี pass ไม่เกิน `pass ของคนที่ถูกเลือก + 1`
   - **Protection:** คนที่ `waitPasses ≥ ceil(จำนวนคนในคิว / 4) + 1` ห้ามถูกข้ามเพื่อเลือกคนที่ยังไม่ถึงเกณฑ์
4. ในกลุ่มที่อนุญาต เลือกกลุ่มที่มีต้นทุนต่ำสุด:

   ```
   ต้นทุนกลุ่ม = คะแนน split ที่ดีที่สุด (Stage 2)
               + 6·(กลุ่ม 4 คนนี้เล่นด้วยกันในช่วงล่าสุด)
               + 1·(เล่นด้วยกันก่อนหน้านั้น)
               + 3·(wait-pass ที่ขาดไปเทียบกับลำดับปกติ)
   ```

   ถ้าการคละได้ประโยชน์น้อย เทอม wait deficit จะทำให้การหมุนตามปกติชนะ ถ้าต้นทุนเสมอกัน ตัดสินด้วยลำดับคิว แล้วจึงใช้ seeded random

**Diversity tracking:** ใช้ประวัติแบบมีขอบเขต 50 แมตช์ล่าสุดที่จบแล้ว
- "ล่าสุด" = `max(2, 2 × จำนวนคอร์ท)` แมตช์ ประมาณ 2 รอบ
- นับแยก: คู่หู, คู่แข่ง, กลุ่ม 4 คน และ exact composition
- ช่วงล่าสุดถูกลงโทษหนักกว่าช่วงเก่า

**Champion Mode:** กติกาแชมป์มาก่อนเสมอ Mix มีผลแค่การเลือก **ผู้ท้าชิง 2 คน** ภายในกติกาเดียวกัน ไม่แยกคู่แชมป์ ไม่ยึดสิทธิ์ ไม่รีเซ็ต streak (มี test และการตรวจใน simulation)

## 5. สูตรให้คะแนนทีม (Weighted Team Scoring)

**Stage 2** ทำงานหลังจาก Stage 1 เลือก 4 คน (หรือผู้ท้าชิง 2 คน) แล้วเท่านั้น จึง**ไม่สามารถ**ข้ามความแฟร์ได้ โดยประเมินทั้ง 3 splits:

```
score = 7·skillGap + 4·recentTeammate + 1·olderTeammate + 1·recentOpponent
        (+ 8·recentExactComposition เมื่อเปิด Mix Groups)
```

| เทอม | ความหมาย |
|---|---|
| `skillGap` | \|ผลรวมฝีมือทีม A − ทีม B\| |
| `recentTeammate` / `olderTeammate` | จำนวนครั้งที่คู่หูในทีมเคยจับคู่กันในช่วงล่าสุด / ก่อนหน้านั้น (ภายใน 50 แมตช์) |
| `recentOpponent` | จำนวนคู่ข้ามทีมที่เคยเจอกันในช่วงล่าสุด |

**Guardrail:** ห้ามเลือก split ที่ gap > `max(gap ต่ำสุดที่เป็นไปได้, 2)` และใช้กฎเดียวกันตอนเลือกกลุ่มใน Stage 1 ด้วย

**ทำไมต้องเป็น 2 ไม่ใช่ "min + 1":** ในกลุ่ม 4 คน ทุก split มีผลรวมฝีมือรวมเท่ากัน gap จึงมีพาริตี้เดียวกันเสมอ (0/2/4 หรือ 1/3) ถ้าใช้ "min + 1" ก็จะเท่ากับ skill-first แบบเดิมทุกประการ เพราะเลือก gap 0 กับ 1 ในกลุ่มเดียวกันไม่ได้ เพดาน 2 จึงเปิดให้แลกได้ไม่เกิน gap 2 ตามน้ำหนัก แต่ห้าม (เก่ง+เก่ง) vs (มือใหม่+มือใหม่) แบบ gap 4 เมื่อมีทางเลือก

**การเลือกน้ำหนัก** (`npm run sim:tune`): 240 runs ต่อชุด, Mix OFF, scenario equal / unequal / lateJoiners / staggered, ค่าในตารางไม่รวม equal

| ชุดน้ำหนัก (gap / คู่หูล่าสุด / คู่หูเก่า / คู่แข่ง) | Fair: gap ≥2 | Fair: คู่หูซ้ำล่าสุด | Champion: gap ≥2 | Champion: คู่หูซ้ำล่าสุด |
|---|---|---|---|---|
| skill-first (≈Phase 1) | 1.8% | 23.0% | 9.1% | 20.8% |
| 10 / 4 / 1 / 1 | 7.0% | 15.3% | 13.2% | 16.4% |
| 8 / 4 / 1 / 1 | 8.6% | 13.3% | 13.7% | 15.8% |
| **7 / 4 / 1 / 1 (เลือก)** | **9.3%** | **11.8%** | **14.3%** | **15.3%** |
| 6 / 4 / 1 / 1 | 10.5% | 10.1% | 15.0% | 14.7% |
| 5 / 4 / 1 / 1 (ค่าเริ่มต้นตามสเปก) | 12.0% | 7.9% | 14.5% | 14.5% |
| 3 / 4 / 1 / 1 | 16.0% | 6.0% | 16.3% | 13.5% |
| 2 / 4 / 1 / 1 | 18.9% | 5.5% | 18.6% | 13.3% |

ทุกชุดมี gap ≥3 ≤ 0.1% (Fair) และ hard violations = 0

**เหตุผลที่เลือก 7:** ลดคู่หูซ้ำล่าสุดได้ครึ่งหนึ่ง (23% → 11.8%) ขณะที่ gap ≥2 อยู่ต่ำกว่า 10% ส่วนค่า 5 ลดคู่หูซ้ำได้มากกว่า แต่ gap ≥2 สูงถึง 12% ซึ่งย้อนผลของ Phase 1 มากเกินไป

กราฟเป็น trade-off ต่อเนื่อง **ไม่มีชุดน้ำหนักที่ดีที่สุดทุกด้าน** และสามารถปรับผ่าน `config.teamWeights` ได้ (มี validation) โดยยังไม่เปิดใน UI ตามสเปก

## 6. ผล Simulation ก่อน vs หลัง

**ชุดทดสอบ:**
- grid: ผู้เล่น {6, 8, 10, 12, 16, 20, 24, 30} × คอร์ท {1–5} × {Fair, Champion} × 8 scenarios × 3 seeds × 24 รอบต่อคอร์ทที่ใช้ได้
- P1 baseline: 1,920 runs (engine Phase 1 ที่ snapshot ไว้ก่อนแก้ ไม่มี Mix)

## 7. Trade-offs ด้านความแฟร์

แยกเป็น 4 ประเภทตามที่สเปกขอ

### ✅ ปรับปรุงที่ยืนยันแล้ว (วัดได้จาก simulation และ test)
- คนมาสายเริ่มที่ระดับต่ำสุดปัจจุบัน ไม่ไล่กินคิว (effective spread 9.71 → 1.26) และไม่มีสถิติปลอม
- คู่หูซ้ำในช่วงล่าสุดลดจาก 32% เป็น 19% และ exact rematch ลดจาก 26% เป็น 14% (Mix OFF)
- Mix ON ลดกลุ่ม 4 คนซ้ำในช่วงล่าสุดจาก 39% เป็น 27% และทั้ง session จาก 53% เป็น 38%
- ไม่มีการละเมิดลำดับความแฟร์ใดๆ ใน 5,760 runs

### ⚖️ Trade-offs (ยอมรับโดยเจตนา และรายงานตรงๆ)
1. **ความสูสีของฝีมือลดลงบางส่วน:** Fair gap ≥2 เพิ่มจาก 2% เป็น 9% (Champion 9% เป็น 15%) ส่วน gap ≥3 ไม่เพิ่ม ผลกระจุกในก๊วนเล็กที่กลุ่มถูกล็อก (8 คน: 1% เป็น 24%) เพราะทางเลือกจริงคือ "แมตช์สูสีแต่ซ้ำทุกคนเดิมทุกตำแหน่ง" กับ "แมตช์ต่างกัน 2 แต้มแต่คู่ใหม่"
2. **Mix ON ทำให้คิวยืดเล็กน้อย:** Fair wait p90 เพิ่ม 0.5 นาทีโดยเฉลี่ย และ max consecutive waits เพิ่มสูงสุด 1–2 ครั้ง (12 → 13) ซึ่งอยู่ในขอบเขต tolerance และ protection ที่กำหนด โดยไม่มีการละเมิด
3. **คนมาสายได้เล่นน้อยกว่าเดิม** (เฉลี่ย 7.3 → 6.0 เกม) ตามเจตนาของฟีเจอร์ A

### ⚠️ ข้อจำกัดที่ทราบ
1. **Session ที่ไม่มีคนรอ** (ผู้เล่นตอนเริ่มลงคอร์ทได้พร้อมกันพอดี: `players % 4 = 0` และ `players / 4 ≤ courts`): scheduler ไม่มีทางเลือกเลย spread ของเกมจริงจึงขึ้นกับระยะเวลาแมตช์และการยกเลิกล้วนๆ
   - พบ worst case spread 10 ใน run หนึ่งที่เปิด Mix ON (20 คน 5 คอร์ท, staggered) ตรวจแล้วทั้งคนที่ได้น้อยและได้มาก **รอรวม 0 นาที** คนแรกเจอแมตช์เฉลี่ย 17.8 นาที คนหลังเจอ 12.2 นาที และ elapsed match duration ต่างกันแค่ 6.4% (ดู 11.3)
   - เทียบเป็นคู่ seed เดียวกันในกลุ่มนี้ (240 คู่) ค่าเฉลี่ย ON−OFF = −0.13 (แย่กว่า 72 / ดีกว่า 86 / เท่ากัน 82) จึงเป็นความแปรปรวน ไม่ใช่ผลของ Mix
   - ในกลุ่มที่มีคนรอ (720 คู่) ON−OFF = +0.03 (แย่กว่า 82 / ดีกว่า 66 / เท่ากัน 572), spread p99 = 2 ทั้งคู่, max OFF 4 / ON 3
   - *แก้ไขในรอบ hardening:* ฉบับแรกใช้นิยาม `players ≤ courts × 4` ซึ่งผิด ตัวเลขข้างบนคำนวณใหม่แล้ว ข้อสรุปเหมือนเดิม
2. **8 คน 1 คอร์ทยังมีกลุ่ม 4 คนซ้ำสูง** (69% แม้เปิด Mix) เพราะคนรอมีแค่ 4 คนพอดีเมื่อคอร์ทว่าง จะคละได้ก็ต่อเมื่อให้คนเล่นติดกันขณะที่อีกคนรอนานกว่า ซึ่งขัดกับหลักการข้อแรก
3. **Tie ของ Mix OFF ยังต้องเริ่มรอในเวลาเดียวกันเป๊ะ** เหมือน Phase 1

### ❓ สมมติฐานที่ยังไม่ได้ทดสอบ
- โมเดลผลแพ้ชนะใน simulation เป็นแบบสังเคราะห์ (logistic ตามผลรวมฝีมือ และค่าเอนเอียงของแชมป์) ผลจริงอาจต่างไป
- น้ำหนักและค่า tolerance ถูก tune จาก metric ที่ simulation วัดได้ ยังไม่มีข้อมูลความพึงพอใจของผู้เล่นจริงว่า gap 2 แลกกับคู่ใหม่ "คุ้ม" หรือไม่
- ระยะเวลาแมตช์ 10–16 นาที (staggered 5–25) เป็นค่าสมมติ
- ยังไม่ได้ทดสอบกับ session จริงหรือ log จริง

## 10. ความเสี่ยงที่เหลือและข้อเสนอแนะ

### ความเสี่ยง
1. **ความสูสีลดลงในก๊วนเล็ก** (8–12 คน gap ≥2 ประมาณ 17–24%) ถ้าผู้เล่นจริงรู้สึกว่าแมตช์ไม่สูสี ควรเพิ่ม `skillGap` (8–10) ซึ่งตาราง tuning แสดงผลกระทบไว้แล้ว
2. **ความซับซ้อนของ Stage 1 ตอน Mix ON** ขึ้นกับ `waitPasses` ซึ่งเป็น state ใหม่ ข้อมูลเก่าเริ่มที่ 0 ในช่วงแรกหลังอัปเกรด การผ่อนลำดับจึงอาจต่างจาก session ใหม่เล็กน้อย (ยังไม่ข้าม effective games)
3. **ประสิทธิภาพ:** ต้นทุนต่อคำสั่งยังโตตามขนาด state (structuredClone ทั้งก้อน) เหมือน Phase 1 ส่วนการคำนวณ diversity ถูกจำกัดที่ 50 แมตช์และไม่เกิน 70 กลุ่ม × 3 splits
4. **คนที่ออกแล้วกลับมาด้วยการ "เพิ่มผู้เล่น" ชื่อเดิม** จะได้ตัวตนใหม่ สถิติแยกกัน ต้องอาศัย host ใช้ปุ่ม "กลับเข้าคิว"

### ข้อเสนอแนะ (ยังไม่ได้ทำ รอการตัดสินใจ)
1. ทดลองกับก๊วนจริง แล้วเก็บ feedback เรื่อง "สูสี vs คู่ใหม่" เพื่อยืนยันค่า `skillGap = 7`
2. พิจารณา preset ใน UI เช่น "เน้นสูสี / สมดุล / เน้นคู่ใหม่" ที่ map ไปยัง `teamWeights` ถ้าก๊วนต่างกันมาก
3. สำหรับ session ที่ไม่มีคนรอ ถ้าต้องการลด spread อาจให้ "แมตช์ยาว" ได้เครดิตลำดับ แต่เป็นนโยบายใหม่ที่ต้องตัดสินใจก่อน
4. ใช้ log จริงที่ปกปิดตัวตนแล้วป้อนเข้า `sim/` เพื่อตรวจโมเดลผลแพ้ชนะและระยะเวลาแมตช์
5. แยก event log ออกจาก state ที่ถูก clone ถ้า session ยาวมาก

> ไม่ได้อ้างว่าอัลกอริทึมแฟร์สมบูรณ์แบบ ทุกตัวเลขข้างต้นมาจาก simulation ที่มีสมมติฐานตามหัวข้อ 7 และจาก automated tests เท่านั้น

## 11. Phase 2 Hardening (ก่อน commit)

วันที่ 2026-10-14 · สถานะ: **รอรีวิว ยังไม่ได้ commit หรือ push**

### 11.1 การทดลองน้ำหนักฝีมือแบบ adaptive

**คำถาม:** แมตช์ gap ≥2 ในก๊วน 8 คนเพิ่มจาก 1% เป็นประมาณ 24% เพราะน้ำหนักฝีมือ (7) ต่ำเกินไปหรือไม่

**วิธี:**
- grid เต็ม 3,840 runs ต่อ candidate (8 player counts × 5 courts × 2 modes × Mix ON/OFF × 8 scenarios × 3 seeds × 24 รอบ)
- seed และ scenario เหมือนกันทุก candidate

### 11.2 นโยบายน้ำหนักที่แนะนำ (สุดท้าย)

**คงน้ำหนักคงที่ `skillGap = 7`** (คู่หูล่าสุด 4 / คู่หูเก่า 1 / คู่แข่งล่าสุด 1) และ **ไม่ใช้ adaptive**

- hook ทดลองถูกถอดออกจาก engine แล้ว production จึงไม่มีโค้ดของนโยบายที่ไม่ได้ใช้
- ยืนยันว่า engine ปัจจุบันให้ผลตรงกับชุดทดลอง w7 ทุกตัวเลข (สุ่มตรวจ 40 runs ตรงกันทั้ง 40)

**Trade-off ที่ยอมรับ:** ก๊วนขนาด 8–12 คนจะมีแมตช์ gap 2 ประมาณ 15–24% (gap ≥3 ยังเกือบ 0) แลกกับการไม่เล่นซ้ำทั้งแมตช์เดิมทุกตำแหน่งบ่อยเกินไป

**ถ้าในอนาคตต้องการแก้จุดนี้**: ตัวแปรที่มีผลจริงคือรูปแบบของ penalty คู่หูเก่า ไม่ใช่น้ำหนักฝีมือ เช่น จำกัดเพดานของ `olderTeammate` ต่อคู่ หรือให้ลดลงตามอายุ ควรทดสอบแบบเดียวกับข้างต้นก่อนนำไปใช้ และควรอิงความเห็นของผู้เล่นจริงเรื่อง "สูสี vs ไม่ซ้ำ" (ยังไม่ได้ทำ)

### 11.3 คำอธิบาย metric: rotation fairness กับ participation statistics

ตอนนี้ simulator และรายงานแยก metric เป็น 3 กลุ่มชัดเจน (`METRIC_GROUPS` ใน `sim/runner.js`)

**1. Rotation fairness** ตอบคำถามว่า "การตัดสินใจของคิวถูกต้องไหม เมื่อดูจากคนที่รออยู่ตอนนั้น"

ประกอบด้วย:
- priority violations (ข้ามคนที่ effective games น้อยกว่า)
- waiting-order / tolerance violations
- เล่นติดกันโดยไม่จำเป็น
- champion rule violations
- จำนวนครั้งที่ถูกข้ามติดกัน
- เวลารอเป็นนาที

**ความยาวแมตช์ไม่ถูกนับในกลุ่มนี้เลย**

**2. Participation statistics** ตอบคำถามว่า "แต่ละคนได้อะไรไปจริงๆ"

ประกอบด้วย:
- spread ของเกมจริง (เฉพาะคนที่อยู่ตลอด session)
- spread ของ effective games
- **elapsed match duration**

ค่าเหล่านี้สะท้อนสิ่งที่ scheduler ควบคุมไม่ได้ด้วย เช่น ความยาวแมตช์ การยกเลิก และการพัก/ออก

**3. Match quality** ได้แก่ ความหลากหลายของคู่หู/คู่แข่ง/กลุ่ม และ skill gap

**นิยาม elapsed match duration:**
- ผลรวมของ `endedAt − startedAt` ของแมตช์ที่ **จบจริง** ที่ผู้เล่นอยู่จนจบ
- ถ้าเปลี่ยนตัวเข้ากลางเกม นับจากเวลาเปลี่ยนตัวเข้า
- แมตช์ที่ถูกยกเลิก และช่วงก่อนถูกเปลี่ยนตัวออก **ไม่นับ** เพราะไม่ได้เครดิตเกม
- แมตช์ที่ timestamp ไม่ครบ **ไม่เดา** แต่นับไว้ใน `elapsedMissing` (ใน 26,880 runs = 0)

**ข้อจำกัดของค่านี้:** เป็น "เวลาที่แมตช์เปิดอยู่บนระบบ" คือช่วงที่ host กดเริ่มจนถึงบันทึกผล **ไม่ใช่เวลาเล่นจริงที่ยืนยันแล้ว** ในแอปจริงขึ้นกับว่า host กดปุ่มตรงเวลาแค่ไหน ส่วนใน simulation เป็นนาทีสังเคราะห์

**ตัวนับ "ถูกข้ามติดกัน" เป็นจำนวนครั้งที่จัดแมตช์ ไม่ใช่เวลา:**
- ถ้าหลายคอร์ทจบพร้อมกันแล้วถูกจัดทีละคอร์ท คนที่ได้ลงคอร์ทหลังจะถูกนับว่า "ถูกข้าม" ทั้งที่รอ 0 นาที
- ใน session ที่ไม่มีคนรอ ตัวนับนี้ขึ้นไปถึง 4–5 แต่เวลารอสูงสุดเป็น **0 นาทีทั้ง 240 runs** ที่ roster คงที่
- จึงต้องอ่านคู่กับเวลารอเป็นนาทีเสมอ

- stage ด้วย `git hash-object -w --path=<file> <snapshot>` + `git update-index --cacheinfo 100644,<sha>,<file>`
- ไม่แตะ working tree และ `--path` ทำให้ line ending ถูก normalize ตาม `core.autocrlf=true`
- ตรวจแล้วว่าผ่าน tests ของ HEAD (53/53)
- **ข้อเสีย:** commit 1 มีแค่ engine/API ของ Phase 1 ส่วน UI ทักษะฝีมือ, simulator, fairness tests และรายงาน Phase 1 จะไปอยู่ใน commit 2 ข้อความของ commit 1 ต้องเขียนให้ชัดว่า "engine/API เท่านั้น"
- ไม่ใส่ `package.json` ของ Phase 1 ใน commit 1 เพราะมีสคริปต์ `sim` ที่อ้างไฟล์ที่ยังไม่มีใน commit นั้น
- ไม่ใส่ `index.html` เพราะฟอร์มฝีมือต้องใช้ `app.js` ของ Phase 1 ซึ่งไม่มี

Commit 2: `git add -A` ส่วนที่เหลือทั้งหมด (= tree ปัจจุบันที่ผ่าน 103 tests)

**หมายเหตุเรื่อง line ending:**
- ไฟล์หลายตัวใน working tree เป็น CRLF เพราะ**สคริปต์ patch ของผมเอง** (Python text mode บน Windows) ไม่ใช่โปรแกรมภายนอก
- เนื่องจาก `core.autocrlf=true` และ index ทุกไฟล์เป็น LF commit จะ normalize เป็น LF เอง ไม่มี diff ปลอม
- ถ้าต้องการให้ working tree สม่ำเสมอ ควรเพิ่ม `.gitattributes` (`* text=auto eol=lf`) ใน commit แยก ยังไม่ได้ทำเพราะเป็นการเปลี่ยนนอกขอบเขต

**ยังไม่ได้รันคำสั่ง git ใดๆ ที่เปลี่ยนสถานะ** (ไม่ได้ stage, commit, push หรือ deploy) ใช้เฉพาะ `git status`, `git diff`, `git log`, `git ls-files`, `git show`, `git archive` และ `git hash-object` (แบบไม่มี `-w`)
